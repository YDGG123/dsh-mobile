## 三、改动分片与依赖

三条轨道并行开发，在"手机端消费"处汇合：

```
轨道 ①  ds-bot fork                   轨道 ②  网关插件                轨道 ③  手机端
├─ 名册发布（需求 8）                  ├─ 团队投影帧（快照+增量）      ├─ 数据源迁移（bridge → 网关）
├─ 群聊卡片六环节（需求 9）            ├─ 卡片帧（需求 10）            ├─ 团队页 UI 对齐（需求 1-4）
└─ 卡片投影（需求 10 来源②）           └─ 配对说明与面板（需求 7）      ├─ 配对入口改造（需求 7）

```

- **快车道**：需求 11、12 完全独立、风险低，可**先做先验**（不单独出包，随最终批次一起构建）。
- **关键路径**：① → ② → ③ 的数据源迁移；手机端 UI 对齐可与数据源迁移同期做，但联调要等 ①② 就绪。
- **收敛点**：需求 8、9、10 全在同一个 `ds-bot` fork → **一次改造、一次重打包**。

## 四、实时状态的传输设计（回应"数据量与延迟"）

结论：**不会成为瓶颈**。依据与规矩：

- 状态帧约 150–250 字节；最坏情况（10 个 Bot 每秒各变 2 次）约 4 KB/s，**远低于手机已在跑的 token 流**（一条回答几十 KB 到上百 KB）。实测常态是每分钟几次变化。
- 网关已有先例可循：v0.10.4 之所以裁剪会话列表投影，就是为了避免**大包**在公网隧道超时——说明要防的是"一次传一大堆"，不是"频繁传一点点"。
- 四条规矩：**快照 + 增量**；**变化合并节流**（300–500 ms 一批）；**静态数据（头像/角色/名字/instructions）一次性取回并本地缓存**，不进状态帧；**重连发快照对齐**，不做事件回放。
- 延迟：WebSocket 长连接，局域网毫秒级；Quick/固定域名多一跳公网，通常几十到两三百毫秒，对状态类信息无感。Quick 与固定域名的差别在**稳定性与地址是否固定**，不在吞吐。

## 五、验收与构建纪律

- 本地自验：`dsh-mobile` 的 typecheck / 单测；`ds-bot` 的 `npm test` / `npm run build` / `npm run lint`；网关插件的测试。
- 设备验证：iOS 16 真机（用户持有）验 16 行为；**iOS 17+/26 靠模拟器**（并在有其它系统用户时收集反馈）；安卓用模拟器/真机。
- 联调路径：网关 + ds-bot 本地装（`file:` 引用）→ 手机端连本机 → 走完配对、名册、实时状态、Bot/群聊聊天、卡片。
- **构建纪律**：所有开发在特性分支；**仅当一批改动全部自验通过后**，合并进 `ios16-support` 触发一次构建，或手动 dispatch。建议同时改造 workflow：**去掉 push 触发**（只留手动）、**自动重跑 3 次降为 1 次**，彻底避免误触发与 runner 浪费。

## 六、风险与红线

1. **改 ds-bot = 改跑着 Bot 团队本身的那一层**。开发全程在 fork 内、用测试与构建产物隔离验证；**安装到 profile 必须是显式决定**，并提前备好回滚（现成先例：`.ds-bot.pre-bridge` + 重打包 `.tgz`）。安装后需重启 DSH，期间的会话会中断。
2. **ds-bot 是 registry 依赖**，插件管理器更新会整包覆盖。耐久路线 = fork 重打包 + `file:` 引用；所有改动保持在 `feat/group-chat-cards` 分支，便于日后 rebase 上游。
3. **iOS 17+ 回归风险**：每一次降级改动都要保留 17+ 路径；17+ 缺少真机验证渠道，是当前最大的验证盲区。
4. **群聊卡片是真特性**（六环节、跨 host+client），不是开关；其中"等卡与轮次推进的语义"需要先定清楚再写代码。
5. **数据源迁移期间**手机端会短暂处于"桥与网关并存"状态，须保证任一路径可用，避免用户拿到半成品。
